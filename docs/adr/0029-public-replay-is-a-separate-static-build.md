# O replay público é um build estático à parte, e a exportação recusa dado pessoal de qualquer cliente

O painel tem um build só para o site público: `pnpm build:replay` liga `COMANDA_PUBLIC_REPLAY=1`, e com ele o `next.config.ts` passa a `output: "export"` (com `trailingSlash`, para qualquer host estático servir `/replay/S-…/index.html`) e a raiz `/` abre a lista de replays em vez da tela ao vivo. Sem a variável, `next dev` e `next build` continuam um app Next.js comum. Ligar o export estático sempre foi descartado: ele proíbe rotas dinâmicas sem `generateStaticParams`, route handlers que leem a requisição, rewrites e headers, e a tela ao vivo e a Fila não devem herdar essas proibições só porque o replay precisa delas; também deixaria a raiz pública numa tela que não tem API para falar. Os replays são páginas `/replay/[sessionId]` geradas no build a partir de `public/replays/index.json`, com `dynamicParams = false`, e o Rastro gravado vai na página; o JSONL continua em `public/replays/` para quem quiser baixá-lo. A reprodução lê o Rastro com o mesmo `web/src/lib/trace` do ao vivo (ADR-0025) e avança um evento por vez, num ritmo pelo tipo do passo, não pelos horários gravados, que teriam longas pausas de latência do modelo ou, num Rastro roteirizado, nenhuma.

`comanda export-replay` só copia um Rastro se nenhum evento tiver nome, telefone ou e-mail de qualquer cliente do banco, conferido com a mesma máscara do relatório da avaliação. A gravação mascara apenas o cliente do próprio atendimento (ADR-0008), e um atendimento adversarial pode trazer o dado de outro, como o C026 pedindo o telefone do dono de um pedido; num replay público isso não pode passar. A conferência pode recusar por engano um texto que use, como palavra comum, parte do nome de algum cliente; aí o erro aponta o evento, e o atendimento fica de fora. O domínio não guarda endereço de cliente, então não há o que conferir além desses três dados.
